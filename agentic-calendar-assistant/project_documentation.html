Project Overview

1.1 Purpose & Goals

The Agentic Calendar Assistant is a production-grade, full-stack web application that gives users the ability to manage their Google Calendar through a natural-language chat interface powered by a Large Language Model (LLM). Rather than navigating calendar UI, users simply type commands like "Schedule a 30-minute standup tomorrow at 10 AM and invite john@example.com" and the AI agent executes the action autonomously.

The project demonstrates modern Agentic AI patterns: the LLM reasons over the user's request, selects the appropriate tool(s) from a predefined toolset, invokes them with correct parameters, and streams a structured reply back to the user in real time.

💡
Agentic AI Pattern
Unlike simple chatbots that only answer questions, this app uses an LLM agent with tools — the model can autonomously decide which Google Calendar API to call, extract structured parameters from natural language, and compose a meaningful response from the API's result.

1.2 Core Features

  • 🗓️ List upcoming meetings — fetch upcoming Google Calendar events (all or today-only)
  • 🆕 Create meetings — create events with title, time, attendees, optional Google Meet link
  • 🔁 Reschedule meetings — move an existing event to a new start/end time
  • ❌ Cancel meetings — delete an event and notify all attendees
  • 🔍 Check availability — check if the user is free/busy in a given time window
  • 💬 Persistent chat threads — conversation history saved per user with multi-thread support
  • 🧠 Working memory — agent stores user preferences (timezone, default length, usual attendees)
  • 🔐 Secure OAuth — Google Calendar OAuth managed via Descope (no raw token handling in app)
  • 🔌 MCP Server — exposes calendar tools as a Model Context Protocol endpoint for AI IDEs like Cursor
  • 🌊 Streaming responses — real-time token-by-token reply via Server-Sent Events (SSE)

2.3 Data Flow Diagram — Chat Request

The following shows the complete lifecycle of a user's chat message through the system:

1
User sends a message in the chat UI
Frontend collects prompt text + current threadId (UUID). Optimistically adds a "Thinking…" bubble to the UI state.
2
POST /api/agent/chat with Bearer token
Frontend sends HTTP POST with { message, threadId } and sets Accept: text/event-stream to open an SSE connection.
3
requireSession middleware validates JWT
Backend calls descopeClient.validateSession(token). On success, extracts authUserId (sub claim) and upserts user into PostgreSQL via ensureUser().
4
streamAgentReply() creates a Mastra Agent
Instantiates new Agent({ model: 'openai/gpt-4o-mini', tools: createCalendarTools(authUserId), memory }) with injected calendar tools and memory store.
5
Agent streams through fullStream
The LLM processes message + thread history. For each tool-call chunk, emits an SSE "progress" event. For each text-delta, emits an SSE "token" event.
6
Tool execution — Calendar Service called
When the agent decides to call e.g. createMeeting, Mastra invokes the tool's execute function. This calls getCalendarAccessToken(authUserId) → Descope API → Google Calendar API.
7
Tokens stream to frontend — UI renders markdown
Each SSE token event appends text to the assistant message bubble in real-time. MarkdownMessage renders with react-markdown + remark-gfm.
8
Thread auto-titled and "completed" emitted
After streaming finishes, if the thread has no title, it's named after the first 80 chars of the user's message. SSE "completed" event is sent, frontend refreshes thread list.

3.3 Backend Services

agent.service.ts — Core Agent Logic

This is the heart of the application. Key responsibilities:

  • streamAgentReply() — Creates a Mastra Agent instance on every request (stateless), passes user's authUserId as the memory resource scoping ID, then iterates agent.stream().fullStream. Emits SSE events for tool calls (progress) and text deltas (tokens).
  • listUserThreads() — Queries Mastra memory for all threads belonging to a user (up to 30, ordered by updatedAt DESC).
  • getThreadMessages() — Validates thread ownership (resourceId must match authUserId), then recalls all messages. Normalizes content to string (handles both string and structured content with parts array).
  • Auto-thread titling — After streaming completes, if the thread has no title, sets it to the first 80 characters of the user's message.

agent-tools.service.ts — Mastra Tool Definitions

Defines 5 Mastra tools that wrap the calendar service. Each tool has:

  • id — unique string identifier the LLM references
  • description — natural language description the LLM uses to decide when to call it
  • inputSchema — Zod schema for parameter validation
  • execute — async function calling the corresponding calendar service method
Tool IDDescriptionKey Parameters
listUpcomingMeetingsList Google Calendar eventsmaxResults (1-20), todayOnly (boolean)
checkCalendarBusyCheck free/busy statusstartIso, endIso (ISO-8601)
createMeetingCreate event + optional Meet linktitle, startIso, endIso, attendeeEmails?, description?, addGoogleMeet?
rescheduleMeetingMove existing event to new timeeventId, startIso, endIso
cancelMeetingDelete event + notify attendeeseventId

calendar.service.ts — Google Calendar API Layer

All Google API calls are funnelled through this service. Key design decisions:

  • OAuth2 client per call: Creates a new google.auth.OAuth2() instance for each request, sets credentials from the fetched access token. Stateless and safe for concurrent requests.
  • formatEvent(): Normalizes the verbose Google API response into a clean object: { id, title, description, location, start, end, htmlLink, meetLink, attendees[] }.
  • createMeeting: Adds a Google Meet link by default (conferenceDataVersion: 1). Sends calendar invites to all attendees (sendUpdates: 'all'). Uses randomUUID() as the conference request ID.
  • listUpcomingMeetings: Supports todayOnly flag that clamps timeMin/timeMax to start/end of current day (midnight to 23:59:59).

connection.service.ts — OAuth Connection Management

  • createCalendarConnectUrl() — Calls Descope's outbound.connect() to generate a Google OAuth authorization URL, saves status: 'pending' in DB, returns the URL for frontend redirect.
  • refreshCalendarConnection() — Calls Descope management API to check if a token exists for the user, updates DB status to 'connected' or 'disconnected'.
  • getCalendarConnection() — Returns current connection status from DB (defaults to 'disconnected' if no row found).

token.service.ts — Access Token Retrieval

Single function: getCalendarAccessToken(authUserId). Calls Descope's management API outboundApplication.fetchToken(appId, authUserId) and extracts the accessToken field. Throws with a descriptive message if token is missing (prompts user to reconnect).

3.5 AI Agent Architecture

🤖
Agent System Design
The Mastra agent uses a ReAct-style (Reason + Act) loop. The LLM reads the system prompt, current conversation thread, and available tools. It then decides whether to call a tool (action) or reply with text. Tool results are fed back into the conversation context, enabling multi-step reasoning.

Agent Configuration

  • Model: openai/gpt-4o-mini (configurable via AI_MODEL env)
  • ID: "meeting-assistant"
  • Memory scope: Per resourceId (= authUserId), meaning each user has isolated memory
  • Thread isolation: Per threadId (UUID), multiple threads per user
  • Last N messages: 20 messages recalled per request to keep context window manageable

Agent Instructions (System Prompt)

The system prompt defines the agent's personality and behavioral rules. Key rules include:

  • Memory usage: Update working memory when the user states preferences. Use thread history before re-fetching.
  • Time handling: "Any time" defaults to tomorrow 10:00 AM local time. Relative times converted to ISO-8601 using injected current time.
  • Response format rules: Different response templates for listing vs. detail vs. action confirmation. Avoids filler phrases. Never invents data not in tool results.
  • Markdown: UI renders markdown — uses bullet lists, bold labels, and [View meeting](url) style links.

Working Memory Template

# Meeting preferences
- Timezone:
- Default meeting length (minutes):
- Preferred meeting hours:
- Usual invitees:

This template is populated as the agent learns user preferences from the conversation. It persists across all threads for a user.

3.6 MCP Server

The app optionally exposes a Model Context Protocol (MCP) endpoint, allowing AI-powered IDEs (like Cursor) to use the calendar tools directly.

  • Endpoint: POST /mcp
  • Auth: Descope-verified JWT (via DescopeMcpProvider)
  • Available tools: listUpcomingMeetings (with maxResults and todayOnly params)
  • Auth scopes required: profile
  • Token extraction: Decodes JWT payload from extra.authInfo.token to get sub (authUserId)
  • Response format: MCP text content: { content: [{ type: 'text', text: JSON.stringify(meetings) }] }
  • GET /mcp: Returns 405 Method Not Allowed (Cursor probes this endpoint)

3.7 Authentication Middleware

The requireSession middleware runs on all /api/connections and /api/agent routes:

// 1. Extract Bearer token from Authorization header
const token = header?.startsWith("Bearer ") ? header.slice(7) : null;

// 2. Validate with Descope
const authInfo = await descopeClient.validateSession(token);

// 3. Extract authUserId from JWT claims (sub)
const authUserId = String(claims.sub);

// 4. Upsert user in PostgreSQL
const user = await ensureUser({ authUserId, email });

// 5. Attach auth context to req.auth
req.auth = { authUserId, email, name, userId: user.id, token: claims };

The middleware exposes two user identifiers downstream:

  • req.auth.authUserId — Descope's user ID (used for memory scoping, token retrieval)
  • req.auth.userId — Internal PostgreSQL UUID (used for connection table lookups)

3.9 Frontend Components

ChatPanel (chat-panel.tsx) — ~500 lines

The primary UI component. Manages all chat state and renders both the sidebar and main chat column.

State:

  • threadId — Current thread UUID (new UUID on "New Chat")
  • messages — Array of { id, role, content } messages
  • threads — List of thread summaries from backend
  • prompt — Current textarea input value
  • running — Boolean: SSE stream in progress
  • loadingThread — Boolean: loading a past thread
  • progress — Current tool-call status string (shown while agent runs tools)

Key behaviors:

  • Optimistic UI: User message and empty assistant bubble added immediately, then filled with streaming tokens
  • SSE streaming: Uses streamAgentChat() which reads the SSE stream byte-by-byte, splits on \n\n, parses data: lines as JSON events
  • Thread switching: resumeThread() loads messages from backend and swaps the current view
  • Suggestion chips: Shown on empty state — clicking sends the suggestion immediately
  • Keyboard: Enter submits, Shift+Enter adds newline in textarea

ConnectionPanel (connection-panel.tsx)

  • Shows current Google Calendar connection status (connected/pending/disconnected) with a colored indicator
  • Connect: Calls connectCalendar() → fetches Descope refresh token → sends to backend → backend returns OAuth URL → redirects user
  • Refresh: Calls refreshCalendarConnection() → backend checks Descope for valid token → updates DB status → re-fetches to update UI
  • Shows a skeleton loader while initially fetching connection status

MarkdownMessage (markdown-message.tsx)

Renders assistant messages as Markdown using react-markdown with remark-gfm (GitHub Flavored Markdown for tables, lists, etc.). User messages are rendered as plain <p> tags with whitespace-pre-wrap.

3.10 Frontend State & Data Flow

apiFetch() utility (lib/api.ts)

Generic fetch wrapper that:

  • Prepends NEXT_PUBLIC_API_URL (defaults to http://localhost:4000) to all paths
  • Adds Authorization: Bearer {token} header if token is provided
  • Sets Content-Type: application/json and serializes body
  • Throws with data.error message on non-OK responses

streamAgentChat() (lib/agent.ts)

Custom SSE reader that:

  1. Opens a fetch() POST with Accept: text/event-stream
  2. Uses a ReadableStream.getReader() to read bytes
  3. Maintains a buffer, splits on \n\n blocks
  4. For each block, finds lines starting with "data:" and JSON-parses them
  5. Calls the onEvent callback for each parsed event

Security Design

ConcernApproach
Authentication All API routes protected by requireSession. JWT validated server-side with Descope SDK on every request. No client-side auth shortcuts.
Authorization Thread ownership validated: thread.resourceId !== authUserId check prevents cross-user thread access. Calendar operations always scoped to the authenticated user's Google token.
OAuth Token Storage Google OAuth tokens never stored in the app's DB. Descope acts as the token broker — tokens are retrieved on-demand via management API and used transiently.
CORS Backend CORS restricted to APP_URL (frontend origin). Credentials allowed for session cookies.
Input Validation All request bodies validated with Zod schemas before processing. Message length capped at 5,000 chars. ThreadId validated as UUID format.
SQL Injection All DB queries use parameterized queries ($1, $2) via pg pool. No raw string concatenation.
Session Security Cookies set with SameSite: Lax and Secure: true in production.
MCP Security MCP endpoint authenticated via Descope MCP Provider. Requires valid JWT with profile scope.

Error Handling Strategy

Backend

  • 401 Unauthorized: Missing token or expired session → { error: "Unauthorized" } or { error: "session expired" }
  • 400 Bad Request: Zod validation failure → { error: "Invalid chat body" }
  • 500 Internal Server Error: Service-level exceptions → { error: message }
  • SSE Error Event: For streaming route, errors are sent as data: {"type":"error","message":"..."} before closing the stream instead of HTTP error codes
  • 503 Service Unavailable: Health check DB failure

Frontend

  • apiFetch errors: Non-2xx responses throw with data.error message
  • SSE error events: Replaced into the assistant's message bubble (the empty placeholder becomes the error text)
  • Thread load failure: Appends a system message "Could not load the chat" to the conversation
  • Network failure: Appends system message "Could not reach the agent API"
  • Connection failures: Silently logged (console.log) — UI shows stale state rather than crashing

Setup & Running Locally

Prerequisites

  • Node.js 20+ and npm
  • Docker Desktop (for PostgreSQL)
  • A Descope project with Google Calendar configured as an Outbound App
  • An OpenAI API key

Step 1: Start PostgreSQL

# From the project root (agentic-calendar-assistant/)
docker compose up -d
# PostgreSQL available at localhost:5442

Step 2: Setup Backend

cd backend

# Install dependencies
npm install

# Configure environment (fill in Descope + OpenAI keys)
cp .env.example .env  # or edit .env directly

# Run database migrations
npm run migrate

# Start development server (port 4000)
npm run dev

Step 3: Setup Frontend

cd frontend

# Install dependencies
npm install

# Configure environment
# Edit .env and set NEXT_PUBLIC_DESCOPE_PROJECT_ID

# Start development server (port 3000)
npm run dev

Step 4: Connect Google Calendar

  1. Open http://localhost:3000 and sign in via Descope
  2. Go to Dashboard → click Connect in the Connections panel
  3. Complete the Google OAuth flow (Descope handles this)
  4. Click Refresh in the Connections panel to confirm status shows "Connected"
  5. Start chatting with your calendar!

npm run migrate  # runs: tsx scripts/migrate.ts
